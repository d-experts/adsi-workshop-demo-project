# Issue 運用ルール（ローカル Markdown）

> 全体像は [development-process.md](./development-process.md)。工程ごとの手順は各スキル（`requirements` / `design` / `tdd-implementation`）を参照。

## 基本方針

**Issue はプロジェクト内の `issues/` フォルダに 1 件 1 ファイルの Markdown で管理する。GitHub は使わない。**

- `gh` コマンド、GitHub Issue / Pull Request、`git push` は使わない（作業環境は GitHub に未ログイン）
- 作業はローカルでの編集と `git commit` で完結する
- Issue ファイルが「起点」かつ「記録ハブ」。調査結果・変更内容・レビュー結果はすべて Issue ファイルに追記する
- PR の代わりに **AI レビュー**を行う（変更内容を Issue に追記し、別セッションの Claude にレビューさせる）
- 実務の GitHub Issue / Jira チケットに相当する

## ファイル名と番号

| 項目 | ルール |
|------|--------|
| 場所 | `issues/` |
| ファイル名 | `NNNN-<slug>.md`（例: `issues/0001-clock-in-button-disabled.md`） |
| 番号 | 4 桁ゼロ埋めの連番。既存の最大番号 + 1（なければ `0001`） |
| slug | 症状を表す英小文字のケバブケース（Windows でも扱えるよう ASCII のみ） |
| テンプレート | バグ: `issues/TEMPLATE-bug.md` / 機能追加: `issues/TEMPLATE-feature.md`（数字で始まらないファイルは採番対象外） |

- `#3`、`Issue 3`、`Issue #3`、`issue 3` などの指定は、番号部分が一致する `issues/0003-*.md` を指す
- 該当ファイルが見つからない・複数ある場合は推測せずユーザーに確認する
- コミットメッセージで参照するときは `(#3)` と書く（例: `fix: 退勤打刻の時刻ずれを修正 (#3)`）

## ステータス

Issue ファイル冒頭の `- ステータス:` 行を書き換えて更新する。

```
未着手 → 調査中 → 対応中 → レビュー待ち → 完了
```

| ステータス | いつ | 誰が |
|-----------|------|------|
| 未着手 | 起票直後 | 起票時に設定 |
| 調査中 | 原因調査（機能追加では仕様の検討）を始めたとき。調査結果の追記時点もこのまま | 調査担当 |
| 対応中 | 修正に着手したとき | 修正担当 |
| レビュー待ち | 修正が終わり「変更内容」を追記したとき | 修正担当 |
| 完了 | AI レビューが通ったとき | レビュー担当 |

レビューで差し戻しになったら「対応中」に戻す。

## 各段階で書くこと

### 1. 起票（ステータス: 未着手）

ユーザーの説明をもとに、テンプレートに沿って Claude が新しい Issue ファイルを作る。
「Issue テンプレートに沿って」とだけ言われたら、内容で選ぶ。不具合（期待と違う動き）なら **バグ**、新しい機能の要望なら **機能追加**。判断できなければユーザーに確認する。

| 種別 | テンプレート | 項目 | 起票時に書かないもの |
|------|-------------|------|---------------------|
| バグ | `issues/TEMPLATE-bug.md` | タイトル（症状を一文で）/ 再現手順（番号付き）/ 期待する動作 / 実際の動作 | 原因・修正方針 |
| 機能追加 | `issues/TEMPLATE-feature.md` | タイトル（やりたいことを一文で）/ やりたいこと / 背景 / 受け入れ条件 | 実装方針・設計・実装計画 |

推測を混ぜず、ユーザーから聞いた事実だけを書く。不明な項目はユーザーに確認する。

### 2. 調査（ステータス: 調査中）

Plan モードなどでコードを調査し、Issue ファイル末尾に `## 調査結果` を追記する。

```markdown
## 調査結果

### 原因
### 影響範囲
### 修正案
```

調査段階ではコードを変更しない。

### 3. 修正（ステータス: 対応中 → レビュー待ち）

修正後、Issue ファイル末尾に `## 変更内容` を追記し、ステータスを「レビュー待ち」にする。

```markdown
## 変更内容

### 何を（変更要約）
### なぜ（原因と方針）
### 検証（確認したテスト）
### 変更ファイル
```

- 修正は **テスト以外の実装で行う**（テスト変更は最終手段。`.claude/rules/testing.md`）
- 回帰テストを追加したら「検証」に書く

### 4. AI レビュー（ステータス: レビュー待ち → 完了）

`/clear` などで **新しいセッション**を開き、レビュー担当として Issue ファイルと変更差分（`git diff` / `git show`）を読ませる。
Issue ファイル末尾に `## レビュー結果` を追記する。

```markdown
## レビュー結果

- 判定: 承認 / 差し戻し
- 指摘:
```

- 承認ならステータスを「完了」にする
- 差し戻しなら指摘を書き、ステータスを「対応中」に戻す
- 観点は `.claude/rules/common/code-review.md`。並列レビューは `multi-agent-review` スキル

## 追記のルール

- 既存の記述は書き換えず、**末尾に追記する**（ステータス行の更新を除く）
- 同じ段階を繰り返すとき（再調査・再修正）は見出しに回数を付ける（例: `## 変更内容（2 回目）`）

## 機能追加（SDD）との関係

機能追加では「2. 調査」の代わりに、機能ごとのフォルダ `docs/feature-N/` で仕様を詰める（詳細は [development-process.md](./development-process.md)）。
Issue ファイルには `## 仕様` を追記し、**`docs/feature-N/` へのリンクと確定した決定の要約**だけを書く。修正・レビューの段階はバグと同じ。

| 用途 | 場所 |
|------|------|
| 機能ごとの `[Question]` / `[Answer]` と確定仕様 | `docs/feature-N/qa.md` |
| 機能ごとの設計メモ（必要なときだけ） | `docs/feature-N/design.md` |
| プロダクト全体の確定した要求・設計・Unit | `docs/requirements/`・`docs/design/`・`docs/units/` |
| 決定事項の要約・承認の記録 | Issue ファイル（`issues/NNNN-*.md`） |

- feature 番号 N と Issue 番号は別の連番。`qa.md` 冒頭と Issue の `## 仕様` で相互にリンクする
- 生の `[Q]/[A]` 往復は Issue に載せない。確定した決定だけを要約する
- 未決の論点がある限り、その仕様に依存する実装に進まない
- 承認ゲート（要求仕様レビュー → 設計レビュー → 実装計画 (Plan) 承認 → テスト観点レビュー）の通過は、Issue ファイルに追記して記録する
